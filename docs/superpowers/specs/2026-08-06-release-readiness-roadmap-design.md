# 第四至第六阶段：体验、稳定性与上线准备设计

## 背景

项目前三阶段已经完成响应式课表工作台、学生工作台和数据统计工作台。重新审计代码后，剩余工作不应继续扩展业务功能，而应沿着三个连续阶段将现有功能收敛为可稳定部署的产品：

1. 第四阶段统一设置与表单体验。
2. 第五阶段验证功能与数据稳定性。
3. 第六阶段完成 Linux、systemd、Caddy 环境的部署与上线验收。

项目不增加登录鉴权。部署目标继续采用 Ubuntu 22.04、systemd、Caddy、Gunicorn/Uvicorn 和 SQLite。

## 已确认的总体路线

采用“依赖优先、保持阶段边界”的实施方式：

- 第四阶段先建立统一交互基础，再迁移各业务表单。
- 第五阶段统一错误模型、补齐数据安全和自动化测试。
- 第六阶段处理生产进程模型、部署预检和真实数据验收。

跨阶段问题必须放入最早能够正确解决它的阶段：PWA 缓存可能造成业务数据陈旧，因此归入第五阶段；Gunicorn 多 worker 重复启动调度器属于生产部署风险，因此归入第六阶段。

## 当前代码审计结论

### 表单与交互

- 多个弹窗分别实现 Teleport、遮罩、Escape 和滚动锁定，缺少统一焦点陷阱、初始焦点和焦点归还。
- `CreateLessonModal`、`LessonEditModal`、`RescheduleLessonModal` 等重复实现课程冲突错误解析。
- 课程编辑中的保存、状态更新和删除没有完整的独立提交中状态。
- 单条删除仍使用 `window.confirm`，批量删除没有明确的二次确认。
- 设置保存缺少提交中、成功和失败反馈；备份恢复状态与其他表单不一致。

### 功能与数据

- Axios 客户端只有基础地址和超时，没有统一错误模型或安全重试策略。
- 后端自动化测试主要覆盖统计服务，课程、学生、模板、批量操作、备份恢复和调度任务覆盖不足。
- 数据库恢复接口会直接覆盖当前文件，上传前没有验证 SQLite 格式和完整性。
- Service Worker 会处理所有同源 GET 请求，存在缓存 `/api/*` 并返回陈旧业务数据的风险。

### 部署

- systemd 使用两个 Gunicorn worker，而 FastAPI lifespan 会在每个 worker 启动 APScheduler，可能重复执行自动完成和滚动生成任务。
- 部署脚本缺少一键预检、部署锁、部署前备份、健康门禁和明确失败报告。
- 当前 `/health` 只能证明进程存活，不能证明数据库和迁移状态可用。
- 备份脚本仅使用日期命名，同一天重复执行会覆盖此前备份。

## 第四阶段：设置与表单体验

### 目标

统一所有弹窗、输入框、确认操作、异步状态和错误提示；优化课程创建、编辑和调课流程；完善暗色模式、键盘操作及无障碍状态。

本阶段允许适度重组字段顺序和分组，但不改变课程业务规则、数据库结构或 API 重试策略。

### 统一基础组件

#### `AppDialog`

- 统一 Portal/Teleport、遮罩、层级、滚动锁定和响应式宽度。
- 支持 Escape 关闭、初始焦点、焦点陷阱和关闭后的焦点归还。
- 提供正确的 dialog、aria-modal、标题和描述关联。
- 提交过程中按业务需要阻止意外关闭。
- 遵循 reduced-motion 设置并兼容明亮、暗色主题。

优先复用项目已安装的 Reka UI 对话框能力，不新增 UI 框架。

#### `FormField`

- 统一标签、必填标记、说明文本、字段错误、禁用和只读状态。
- 自动建立 label、input、description 和 error 的可访问关联。
- 保留原生输入控件语义和浏览器校验能力。

#### `AsyncButton`

- 统一默认、提交中、成功前等待和禁用状态。
- 防止重复提交并保持按钮宽度稳定。
- 使用可读文案表达状态，不只依靠加载图标。

#### `InlineAlert`

- 统一成功、警告、错误和可恢复状态。
- 错误使用 `role="alert"`，非紧急进度使用适当的 live region。
- 支持可选重试动作和字段级错误摘要。

#### `ConfirmDialog`

- 替换所有 `window.confirm`。
- 展示操作对象、影响范围和不可逆后果。
- 主按钮文案必须描述具体动作，例如“删除 4 节课程”。

### 课程表单结构

采用已确认的 B“上下文优先 + 自适应分组”：

- 顶部先展示学生、原日期、时间和状态等任务上下文。
- 主体按“时间安排 / 课程状态 / 补充信息”分组。
- 桌面端采用双列字段，移动端退化为单列。
- 底部使用固定操作区，持续展示取消、主操作和提交状态。
- 创建、编辑和调课共享字段展示与错误基础设施，但保留各自 API 和业务动作。

#### 创建课程

- 先选择学生，再填写日期、开始时间、课时和备注。
- 显示基于学生课时费的预估金额。
- 冲突错误必须列出冲突学生、日期和时间，并允许修改后重新提交。

#### 编辑课程

- 摘要区展示当前课程对象和状态。
- 快捷状态动作与字段编辑分区，避免把“完成课程”和“保存表单”混为一个提交。
- 保存、状态更新和删除分别维护独立提交状态。
- 调课作为明确的次级动作进入调课流程。

#### 调课

- 清晰对比原课程与目标日期、时间和课时。
- 调课范围选择沿用“仅本次 / 本次及以后 / 修改模板”，但使用统一对话框。
- 冲突信息与创建、编辑使用同一错误展示模型。

### 其他表单

- 学生、模板和设置表单迁移到统一基础组件。
- 设置页增加保存中、成功和失败状态。
- 主题切换保持即时预览；保存失败时恢复上次有效配置。
- 备份下载和恢复使用统一异步状态。
- 移除无实际用途的本地令牌重置入口，不增加登录鉴权。

### 危险操作确认等级

- 删除课程、批量删除、取消课程和删除模板：标准二次确认。
- 数据恢复和覆盖数据库：选择文件后仍须输入“确认恢复”。
- 保存、完成和恢复课程等可逆操作：不弹确认，只显示执行状态和结果反馈。

### 第四阶段验证

- 为所有共享基础组件编写组件测试。
- 为创建、编辑、调课、学生、模板和设置表单覆盖成功、失败、重复提交和关闭行为。
- 使用键盘验证 Tab 顺序、Escape、焦点归还和确认对话框。
- 在 1440×900 与 390×844 下验证布局、暗色模式和 44px 触控区域。

## 第五阶段：功能与数据稳定性

### 统一 API 错误和重试

- 建立集中式错误模型，区分网络中断、超时、服务端错误、校验错误和课程冲突。
- 页面显示用户可理解的文案，同时保留状态码和诊断信息。
- 仅对 GET 请求自动重试，采用短暂退避，最多重试两次。
- 所有写操作禁止自动重试，由用户主动重新提交。
- 日期、学生和统计区间快速切换时取消旧请求或忽略过期结果。

### 课程状态和冲突矩阵

- 覆盖待上、已完成、请假和已调课之间允许及禁止的状态变化。
- 覆盖单条与批量完成、请假、恢复和删除。
- 覆盖时间重叠、边界相接、跨午夜、模板生成和调课后的冲突。
- 批量操作使用事务语义：任一项失败时整体失败，不产生部分更新。

### 后端测试分层

- 服务层：课程、学生、模板、统计、备份恢复和调度任务。
- 路由层：参数校验、错误响应、批量操作和文件上传。
- 集成层：临时 SQLite 数据库和真实 FastAPI 应用，验证前端依赖的响应结构。
- 调度层：自动完成和滚动生成必须可重复执行且不产生重复数据。

### 数据库恢复安全

- 上传后先验证 SQLite 文件头、可打开性和 `PRAGMA integrity_check`。
- 在同一文件系统写入临时文件，验证完成后原子替换当前数据库。
- 替换前生成包含日期和时间的旧库副本。
- 任一步失败时保持当前数据库不变，并删除无效临时文件。

### 日期、时区和统计边界

- “今天”以项目配置时区为准，避免浏览器本地时区与后端不一致。
- 覆盖周一/周日起始、月末、跨年、闰年和历史同期区间。
- 固化收入、有效课时、完成率、请假和调课的回归口径。

### PWA 数据一致性

- Service Worker 永不缓存 `/api/*`。
- 带哈希静态资源使用缓存优先，页面导航使用网络优先并提供离线回退。
- 新版本就绪后提示用户刷新，不在表单操作中强制更新。
- 激活新版本时删除旧缓存，并测试从现有 `kebiao-cache-v1` 升级。

### 第五阶段验证

- 前端纯逻辑、组件、页面和 API 行为测试全部通过。
- 后端服务、路由和集成测试全部通过。
- 前后端联调覆盖核心读写流程及结构化错误。
- PWA 升级、断网和恢复场景没有陈旧 API 数据。

## 第六阶段：部署与上线验收

### 一键只读预检

新增 `app/deploy/preflight.sh`，默认只读并检查：

- Ubuntu、运行用户、目录结构和权限。
- Python、Node.js、npm、SQLite、Caddy 和 systemd 版本。
- `.env` 必填项、数据库路径、CORS 和未替换的默认示例值。
- Python 虚拟环境、依赖导入、Alembic current/head。
- SQLite 完整性、数据/备份/日志目录写权限。
- Caddy 配置、systemd 服务、端口占用和后端导入。
- 前端锁文件、依赖安装条件和生产构建。

脚本输出通过、警告、失败汇总；存在失败项时返回非零状态，不自动修复服务器。

### 生产进程模型

当前单教师 + SQLite 场景将 Gunicorn 调整为一个 worker，确保 APScheduler 只启动一次。调度任务必须具备幂等测试和可识别的启动日志。

多 worker 与独立调度服务属于未来扩展，不纳入本轮上线范围。

### 部署门禁流程

部署脚本按以下顺序执行：

1. 获取部署锁。
2. 运行一键预检。
3. 创建数据库一致性备份。
4. 根据锁文件安装依赖，前端使用 `npm ci`。
5. 执行数据库迁移。
6. 完成前端生产构建和后端编译检查。
7. 验证 Caddy 和 systemd 配置。
8. 重启后端并轮询就绪接口。
9. 就绪后再重载 Caddy。
10. 输出版本、迁移、备份和健康检查摘要。

### 健康与就绪

- `/health` 保留为进程存活检查。
- 新增 `/health/ready`，验证数据库可连接、必要表存在且迁移状态可用。
- systemd 显示 running 不能替代就绪检查。

### 真实数据演练

- 在生产变更前创建并验证备份。
- 使用真实数据库副本演练迁移、完整性检查和恢复，不使用唯一生产库试错。
- 从旧版本数据库执行所有迁移并核对核心表数量与统计结果。
- 桌面端与 390px 移动端走查课表、学生、统计、设置和所有表单。
- 覆盖创建、编辑、调课、状态、批量操作、导出、备份、恢复、断网和服务重启。
- 验证明亮、暗色、键盘操作和 PWA 版本更新。

### 第六阶段交付物

- 一键预检脚本。
- 改进后的部署、备份和恢复脚本。
- Linux/systemd/Caddy 部署说明。
- 上线验收清单及执行记录模板。
- 数据库迁移、恢复和失败处置说明。
- PWA 版本更新说明。

## 阶段依赖与验收顺序

```text
第四阶段 UI 基础
  → 业务表单迁移
  → 第四阶段双端与无障碍验收
  → 第五阶段 API 与数据安全
  → 自动化和联调覆盖
  → PWA 数据一致性
  → 第六阶段预检与进程模型
  → 真实数据副本演练
  → 生产部署与回归
```

每个阶段单独形成实施计划、隔离分支和验收记录。后续阶段不得以跳过前一阶段失败项为前提继续上线。

## 非目标

- 不增加登录鉴权、账户体系或多租户。
- 不新增收费、消息通知或其他业务模块。
- 不迁移到其他数据库或容器平台。
- 不在本轮引入多节点、高可用或自动 CI/CD 部署。
- 不改变已经确认的课程、学生和统计核心业务口径，除非稳定性测试证明现有行为错误。

## 总体完成标准

- 第四阶段：所有表单使用统一交互基础，课程流程清晰，键盘、暗色和危险操作状态可验证。
- 第五阶段：核心业务、日期边界、数据恢复和 PWA 更新均有自动化证据。
- 第六阶段：一键预检全绿，真实数据副本演练成功，部署后就绪检查通过，双端回归无阻断问题。
