# 第五阶段：功能与数据稳定性设计

## 背景与目标

第四阶段已经统一表单、弹窗、危险操作确认和异步反馈。第五阶段采用“依赖优先”的实施顺序，先建立前后端共用的请求诊断与错误语义，再验证业务规则、数据库恢复、日期统计和 PWA 数据一致性。

本阶段不增加登录鉴权，不改变部署目标。完成标准是核心读写流程、结构化错误、事务回滚、日期边界、数据库恢复和 PWA 更新均有自动化证据。

## 实施顺序

1. 统一 API 错误、请求编号和 GET 重试。
2. 固化课程状态、冲突规则和批量事务语义。
3. 加固数据库恢复流程并补齐后端分层测试。
4. 固化项目时区与统计边界。
5. 重构 Service Worker 更新和缓存策略。
6. 执行前端、后端、临时数据库和核心联调验收。

## API 稳定性

### 请求编号

- 前端在每次逻辑请求开始时生成请求编号，通过 `X-Request-ID` 发送。
- 同一个 GET 请求的所有重试沿用同一请求编号，便于将多次传输识别为一次用户操作。
- 后端中间件接收请求编号；缺失或格式无效时生成新的编号。
- 后端在响应头中原样回传最终请求编号，并将请求方法、路径、状态码、耗时和请求编号写入日志。
- 前端错误对象优先读取响应头编号；网络中断时保留本地生成的编号。

请求编号只用于诊断，不作为幂等键、认证信息或业务主键。

### 集中错误模型

前端建立统一的 `AppError`，至少包含：

- `kind`：`network | timeout | server | validation | conflict | unknown`。
- `message`：面向用户的简明中文文案。
- `status`：可选 HTTP 状态码。
- `requestId`：请求编号。
- `detail`：可选服务端诊断内容。
- `retryable`：当前错误是否允许用户主动重试。

映射规则如下：

- 没有响应且非超时：`network`。
- Axios 超时或取消前的超时标记：`timeout`。
- HTTP 502、503、504 和其他 5xx：`server`。
- HTTP 422：`validation`。
- HTTP 409 或结构化 `time_conflict`：`conflict`。
- 其余无法识别的异常：`unknown`。

现有 `parseFormError` 改为使用集中错误模型，不在业务组件中重复解析 Axios 响应。

### 自动重试

- 只对 GET 自动重试。
- 仅重试网络中断、超时、502、503、504。
- 首次失败后最多重试两次，因此一次逻辑请求最多传输三次。
- 使用短暂递增退避；测试通过注入计时器避免真实等待。
- POST、PUT、PATCH、DELETE 永不自动重试。
- 主动取消的请求不重试，也不显示为网络错误。

### 页面数据与过期响应

- 刷新失败时保留最后一次成功数据，不清空课表、学生详情、模板或统计结果。
- 错误区域显示简明文案与“重新加载”操作。
- 用户可展开诊断详情，查看错误类型、状态码、请求编号和服务端信息；默认保持收起。
- 日期、学生、统计区间快速切换时使用请求序号或 `AbortController`。新请求开始后，旧响应不得覆盖新数据。
- 请求取消属于正常控制流，不产生错误提示。

## 课程规则与事务

### 状态矩阵

后端服务层是状态转换的唯一规则来源。允许的显式转换为：

| 当前状态 | 允许操作 | 目标状态 |
|---|---|---|
| 待上 | 完成 | 已完成 |
| 待上 | 请假 | 请假 |
| 待上 | 调课 | 已调课，并创建新的待上课程 |
| 已完成 | 恢复 | 待上 |
| 请假 | 恢复 | 待上 |
| 已调课 | 恢复 | 待上，并解除调课关联 |

相同状态重复提交可作为幂等成功返回；其他未列出的转换返回结构化 409 错误，不修改数据。删除不是状态转换，但必须服从单条与批量事务规则。

### 结构化业务错误

业务拒绝响应包含稳定代码和用户文案，例如：

```json
{
  "detail": {
    "error": "invalid_status_transition",
    "message": "已完成课程不能直接标记为请假",
    "from_status": "已完成",
    "to_status": "请假"
  }
}
```

冲突响应继续使用 `time_conflict`，并保留冲突课程、学生、日期、开始时间和时长。

### 冲突检测

- 同一天相交时间段视为冲突。
- 一节课结束时间等于另一节课开始时间时不冲突。
- 跨午夜课程按真实结束时间检查相邻日期，不把它截断在当天。
- 创建、编辑、恢复、调课和模板生成共用同一冲突判断。
- 调课检测目标时间时排除原课程，但不排除无关课程。
- 模板批量生成遇到已存在等价课程时保持幂等，不生成重复数据。

### 批量事务

- 批量完成、请假、恢复和删除先加载并验证全部课程。
- 任一 ID 不存在、状态非法或恢复产生冲突时，整体失败。
- 验证全部通过后在一个数据库事务内写入并提交。
- 服务函数不得在循环中调用会自行 `commit()` 的单条函数；单条和批量操作共享不提交的内部规则函数。
- 失败时执行回滚，响应包含失败课程 ID 和稳定错误代码，不产生部分更新。

## 后端测试分层

### 测试基础设施

- 使用 pytest、FastAPI TestClient 和临时 SQLite 数据库。
- 通过依赖覆盖向真实应用注入测试 Session。
- 每个测试隔离数据库文件或事务，禁止读写开发数据库。
- 时间相关服务通过显式时钟或 monkeypatch 固定时间。

### 覆盖层次

- 服务层：课程、学生、模板、统计、调度器和恢复服务。
- 路由层：参数校验、响应结构、请求编号、批量错误和文件上传。
- 集成层：真实 FastAPI 应用与临时 SQLite，覆盖前端依赖的核心读写链路。
- 调度层：自动完成和滚动生成重复执行不产生重复数据。

## 数据库恢复安全

数据库恢复从路由文件中拆出专门服务，执行以下顺序：

1. 在当前数据库所在目录创建唯一临时文件。
2. 流式写入上传内容，并限制为配置允许的最大体积。
3. 验证文件头为 SQLite 格式。
4. 以只读方式打开文件，执行 `PRAGMA integrity_check`，结果必须为 `ok`。
5. 验证应用所需核心表和迁移版本存在。
6. 对当前数据库创建带日期和时间的 SQLite 一致性备份。
7. 关闭或释放当前数据库连接，再使用同一文件系统的原子替换切换数据库。
8. 重新建立连接并执行最小读取验证。
9. 删除临时文件；返回备份路径和请求编号。

上传无效、完整性检查失败、备份失败或替换失败时，当前数据库保持不变。所有失败路径都清理无效临时文件；若替换后最小读取失败，立即使用刚生成的旧库副本恢复。

## 日期、时区与统计口径

### 业务日期

- 后端 `today()` 始终读取项目设置时区。
- 前端从设置接口获取时区，用共享日期工具生成业务“今天”，不直接使用浏览器本地日期切片。
- API 的日期字段继续使用 `YYYY-MM-DD`，时间字段继续使用本地业务时间，不在本阶段改为 UTC 时间戳。

### 边界覆盖

- 周一和周日起始。
- 月末、跨月、跨年。
- 闰年 2 月 29 日。
- 日、周、月历史同期区间。
- 配置时区与浏览器时区不一致的“今天”。

### 固定统计口径

- 预计收入：待上与已完成课程价格之和。
- 实际收入：已完成课程价格之和。
- 有效课时：待上与已完成课程时长之和。
- 完成率：已完成数量除以待上与已完成数量；分母为零时为 0。
- 请假数：状态为请假的课程数量。
- 调课数：状态为已调课的原课程数量，不重复计算新课程。

前端卡片、导出和后端统计接口必须使用相同口径。

## PWA 数据一致性

### 缓存策略

- Service Worker 对 `/api/` 和 `/api/v1/` 直接执行网络请求，不读写 Cache Storage，也不提供 HTML 离线回退。
- 带内容哈希的静态资源使用缓存优先。
- 页面导航使用网络优先；离线时返回预缓存的离线页面。
- `manifest.json`、图标和离线页面可预缓存。
- 不把未带版本的 API 响应或用户数据写入缓存。

### 更新流程

- 新 Service Worker 安装完成后进入等待状态，不在安装事件中立即 `skipWaiting()`。
- 页面检测到等待中的新版本后显示非阻断更新提示。
- 用户确认刷新时向等待中的 Worker 发送 `SKIP_WAITING`。
- `controllerchange` 后刷新一次页面，并防止刷新循环。
- 激活时删除所有非当前版本缓存，包括 `kebiao-cache-v1`。
- 表单提交期间不自动刷新页面。

### PWA 自动化验证

- API GET 在在线、离线和恢复后均不命中缓存。
- 哈希静态资源可离线读取。
- 页面导航断网时显示离线页面。
- 从 `kebiao-cache-v1` 升级会删除旧缓存。
- 更新提示、用户确认和 `controllerchange` 刷新各发生一次。

## 验收与提交边界

第五阶段完成前必须具备以下证据：

- 前端纯逻辑、组件、页面、API 和 Service Worker 测试全部通过。
- 后端服务、路由、调度和临时数据库集成测试全部通过。
- 前后端联调覆盖读取、创建、状态更新、冲突、批量回滚、统计和恢复错误。
- GET 重试保持请求编号，写请求不重试。
- 快速切换不会被过期响应覆盖。
- 恢复失败不改变当前数据库。
- PWA 升级和断网恢复后不存在陈旧 API 数据。
- 前端生产构建和后端导入/迁移检查通过。

各实施批次使用独立、可回滚提交。第五阶段不包含生产 systemd/Caddy 进程模型、真实生产数据演练或服务器上线，这些留在第六阶段。
